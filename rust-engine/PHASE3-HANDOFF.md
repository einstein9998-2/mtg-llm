# Phase 3 handoff: what the engine gives a policy/value learner (2026-10-01)

All of this is in `mtg-view` and works on the real eight-deck pool. Nothing here reads hidden state: an agent holds a `SeatView`, which is bound to one seat and cannot name the other seat, engine objects, hashes or raw events (compile-tested in `crates/mtg-fuzz/tests/agent_api.rs`). The raw `Game` accessors (`observe(seat)`, `pending()`, `state_hash()`, `raw_state()`) exist only with the `diff-harness` feature, which agent crates must not enable.

## Loop primitives
- `Game::new(db, [&deck0, &deck1], seed, GameConfig)`, `g.advance() -> Status` (runs the engine to the next decision; `Status::NeedDecision(seat)` says who acts), `g.seat_view(seat) -> SeatView`, `view.observe() -> Observation`, `view.decision()`, `g.apply(decision_id, option_index)`: a decision is an index into the decision's option list (canonical order, interchangeable options collapsed). Option 0 is Pass at priority.
- Decision ids count per seat and the view ids of cards are per seat too, so neither says anything about the other seat's hidden choices (a scry, an Aether Vial activation).
- `SeatView::fork(seed, &dyn BeliefModel) -> Game` at that seat's own decision: a plain clone with the opponent's hidden cards re-sampled from the decklist minus what the seat can identify. Sampled identities are dealt to hand and library positions at random, so a fork says nothing about which unknown card sits where; the opponent's private knowledge and secret picks (Show and Tell, Stronghold Gambit) are reset or resampled. About 10 us. Forks at the other seat's decision are refused (`ForkError::NotObserversDecision`).
- `GameRecord` / `replay`: seed plus action list reproduces a game bit for bit (engine version, hash schema, config and checkpoint hashes are carried; a record with missing or out-of-order checkpoints is refused). Records and `Game::state_hash` are harness material: they contain hidden state and belong to the training harness, never to an agent.

## Search and policies (`sim.rs`)
- `Policy` trait (`choose(&mut self, &SeatView, n_options) -> usize`), `RandomPolicy`, `FirstOption`, `playout(g, [pol0, pol1], max_decisions)`, `score(result, seat)`.
- `FlatMc::new(model, samples, max_rollout, seed).evaluate(&seat_view) -> Vec<f64>`: for each option, fork `samples` worlds, take the option, play both seats randomly to the end, mean score. Replace the random rollout policy with a network and the mean with a value head to get the next step (determinized MCTS / PIMC).
- Sanity result: flat MC at 4 samples beat a random player 78 to 18 over 96 mixed-deck games (`mcmatch`), about 8.5 ms per agent decision in a debug build with other jobs running, 27.5k agent decisions in 235 s.

## Encoding for a network (`encode.rs`)
- `encode_state(&Observation, n_defs, &mut Vec<f32>)`: 11 blocks of `n_defs` counts (my hand, my graveyard, my battlefield, my tapped battlefield, opp battlefield, opp tapped battlefield, opp graveyard, stack, my known library top, my exile, opponent's exile) then `N_SCALARS` = 46 scalars (`SCALAR_NAMES`: life, library sizes, lands played, mana pool, step, designations such as the Ring level and the dungeon, and so on). `state_len(n_defs)` gives the length.
- `encode_options(&Observation) -> Vec<OptionFeat>`: one row per option: kind, decision kind, subject def + 1 (also filled for walker options such as "choose a card from my library"), subject zone, value. Attack options carry the attack target. Intended as embedding lookups; the policy is a softmax over the rows.
- `n_defs` is `db.defs.len()` (pool plus tokens and faces). The card list for the 8 decks is 144 non-basic cards.

## Self-play dump (`selfplay` bin)
`selfplay <decks dir> <games> <out.jsonl> [random|mc] [samples]` writes one JSON line per non-trivial decision: acting seat, sparse state encoding (index/value pairs), option features, chosen index, and the result for that seat filled in at game end; def names are included so a trainer can build its own vocabulary.

## The `mtg-agent` crate (search, net, batched environment, trainer)

Everything here is agent-side: it holds `SeatView`s only and is built against `mtg-view` without the `diff-harness` feature (a test builds it alone to prove that). The frozen core is untouched.

- **Determinized MCTS** (`mcts.rs`): `search(&seat_view, &belief_model, &mut evaluator, &SearchConfig) -> SearchResult { visits, q, value }`. Every iteration forks one world consistent with what the acting seat knows and descends a tree shared across worlds, keyed by option index; PUCT selection, optional root noise. `MctsPolicy` plugs it into the `Policy` trait. A node whose seat or option count differs in some world (the opponent's conditional decisions) is treated as a leaf there.
- **Evaluators**: `RolloutEvaluator` (uniform priors, random-playout value; the no-network baseline) and `NetEvaluator` (a `Net` forward pass on the acting seat's observation). `Evaluator::eval(&world, seat, n_options) -> Eval { priors, value }` is the one interface a stronger model needs.
- **Net** (`net.rs`, `python/mtg_net.py`, `python/train.py`): a sparse-input MLP trunk, a value head and a policy head that scores each option by a dot product with an option embedding (kind, decision kind, subject card, zone, value). Trained in PyTorch (GPU if present), exported to a flat f32 file (`MTGNET01`), loaded and run on the CPU inside the search. Tests: Rust forward vs a pure-Python reference (`test_net.py`, differences about 1e-7) and torch forward vs the Rust forward on an exported net (`test_train.py`, about 1e-7). Weights files change only when the architecture does; the architecture is documented at the top of `net.rs` and in `train.py` and the two must stay in sync.
- **Batched environment** (`env.rs`, `envserver` bin, `python/mtg_env.py`): N games in lockstep, one observation (sparse state encoding plus option features) per game awaiting a decision, answers are option indices, trivial decisions applied internally, autoreset, a game that panics (a runaway engine state) is reported as a truncated draw and restarted. JSON lines over stdin/stdout, standard-library Python client, protocol test `python/test_env.py` (about 9.5k decisions/s through the pipe with 32 games; a binary protocol is the next step if the profile asks for it).
- **Data and loop**: `mctsdata <decks> <games> <iterations> <out.jsonl> [--net w.bin] [--threads T]` plays self-play with both seats searching and logs state, options, visit-count policy target, root value and result per decision (plus `.meta.json` and `.defs.json`). `python/train.py` fits policy cross-entropy on the visit distribution and value MSE on the result. `python/selfplay_loop.py` runs generations: rollout-guided data, train, then net-guided data, with an arena after each (`mctsmatch` vs random and vs rollout MCTS).
- **First numbers** (sandbox, 4 shared cores, debug-free release build): rollout MCTS with 16 iterations beat random 13 to 3 over 16 games at about 29 ms per decision; with a net the cost per iteration drops from about 3 ms (rollouts) to about 0.15 ms. An untrained random net loses to random play, as it should. Nothing has been trained to strength yet: that is the next experiment (needs a few thousand self-play games per generation and the GPU for the larger nets).
- **Known limits**: a fork ignores known library positions (after Thassa's Oracle, Dig, Raph & Mikey), so search worlds can place a card the observer knows is on the bottom elsewhere; the belief model is the uniform decklist model; the opponent inside the tree plays by the same priors as the acting seat (no opponent modelling yet); games with more than 60,000 live objects (an Ocelot Pride copy loop) are declared draws.

## Costs
Random play 500 games/s on one core without checks (release). Clone 2.4 us, fork 10 us, observe 2.8 us. A 1,000-game random batch is therefore seconds; flat MC with 4 samples is about 100 decisions/s per core in debug, which is the number to beat with a network-guided search.

## Caveats
- The engine core is a freeze candidate, not frozen; state hashes (goldens) changed with the rules fixes of M3d and again with the review fixes of M3f (then `ENGINE_CORE_VERSION` 3, `HASH_SCHEMA` 2; now 5 and 4 after RFC 0003), so any stored `GameRecord` or self-play dump made before that must be regenerated, and the encoder layout changed (11 blocks, 46 scalars).
- A fork is only as good as the belief model: two sampled worlds differ in hidden cards, positions and secret picks, and nothing else. Do not hand the true state, a raw `Game` or a `GameRecord` of the live game to an agent.
- The belief model is uniform over decklist minus known cards. Triumph of Saint Katherine's pile order and the opponent's sideboard are not modelled.
